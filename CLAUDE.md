# CareBoard: project guide for Claude Code

CareBoard is a role-aware health analytics app. The database, not the application, decides what each person may see. An approval-gated AI agent (Tiffany) and an assistant (Carey) sit on top, tested by an adversarial evaluation suite. All patient data is synthetic. ## Architecture invariants (do not break; each has tests)
1. **Access is enforced in PostgreSQL row-level security.** `withRole(user, fn)` runs `BEGIN; SET LOCAL ROLE role_x; set_config('app.clinic_id', ...); set_config('app.user_id', ...)`. Roles: `role_admin`, `role_clinician`, `role_executive`, `role_nurse` (NOLOGIN). Login role `careboard_api` is NOINHERIT, NOSUPERUSER, NOBYPASSRLS. Never add application-side filtering as a substitute for a policy.
2. **No FORCE ROW LEVEL SECURITY.** Tested: it makes `app.care_risk_summary()` return 0 rows for executives and breaks fixtures. `test_rls_posture.ts` checks the catalog instead. Do not reintroduce FORCE without re-running that experiment.
3. **SECURITY DEFINER functions** (`app.clinic_contacts`, `app.can_message`, `app.care_risk_summary`, ...) are owned by the table owner and pin `search_path`. Any new one must too.
4. **Insert-only tables:** messages, record_checks, stock_counts. No update or delete grants.
5. **Executives and admins cannot read nurse messages or nurse drafts.** Admin policies exclude `role = 'nurse'` runs and `type = 'handoff_message'` actions.
6. **Agent rules (agent.ts):** tools are allow-listed per role (`ALLOWED`); tier-2 actions (emails, messages) are stored pending and need human approval; the model supplies only a reason or draft text, the server builds emails from database values; kill switch and send log exist; every step is traced.
7. **Runtime guards:** `scope.ts` refuses diagnosis/dosing/treatment in code before any model or tool call (also in Carey). The grounding gate (`ungrounded()` in evalChecks.ts) sends an answer back once if it states a figure no tool returned, then refuses. The nurse agent is excluded from the gate because it has no analytics tools.
8. **Patients are identified by patient number only** in agent output and emails. No names or birth dates leave the database through the agent.

## Commands
Run from `api` unless noted. Local database: Postgres with pgvector (see README setup order).
```powershell
npm test                      # test:unit then test:db (10 files)
npm run test:unit             # no database needed
npm run test:db               # needs local DB with all apply_* scripts applied
npx tsx scripts/apply_X.ts    # apply a migration locally; add --neon for Neon
npx tsx scripts/test_rls_posture.ts [--neon]
npm start                     # API on port 4100
# web folder:
npm run dev                   # Vite dev server
npx tsc -b                    # type check (also run by npm run build)
```
Evaluation (calls a model; uses free-tier tokens):
```powershell
npx tsx scripts/clear_agent_runs.ts
npx tsx scripts/run_evals.ts --repeat=3     # full run, writes eval/results/latest.json and docs/eval-report.md
npx tsx scripts/run_evals.ts --only=X5      # partial run, writes partial.json only
```
Model settings live in `api/.env` as `GROQ_API_KEY`, `GROQ_BASE_URL`, `GROQ_MODEL` (OpenAI-compatible; any provider works). Results from different models are reported separately, never merged. `.env.groq` is a backup of the Groq settings if present.

## Deploy rules
- Never commit `.env` files. Check `git status` before every commit.
- **Order matters:** apply database migrations to Neon (`--neon`) BEFORE pushing server code that needs them. Render redeploys on every push to `main`.
- After a deploy, check https://careboard-1755.onrender.com/api/health and the Actions run.
- Free tier: Render sleeps after 15 min idle (UptimeRobot pings `/api/health` every 5 min); 750 instance hours per month.
- Re-seeding Neon resets demo display names (SQL update for user ids is documented in the README conversation history; ask Angel).

## Definition of done for any change
1. Tests written first or alongside; `npm test` green locally; `npx tsc -b` clean in `web`.
2. If agent behavior changed: add or update eval cases in `api/eval/cases.ts` and re-run the affected cases.
3. If a table, policy or function changed: migration is idempotent, has a check in its `apply_*.ts`, and `ci_setup.sh` applies it in the right order on a clean database.
4. README and `docs/` updated only with numbers that were actually measured. Say "not measured" otherwise.
5. Commit message states what and why. Push only after Angel says yes.
