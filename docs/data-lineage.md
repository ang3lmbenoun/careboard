# CareBoard data lineage

Where each table's data comes from, how it gets into the database, and how to refresh it.
Written 2026-11-15 from the repository files only. I did not connect to any database, so row counts below are counts of the committed CSV files, not of any live database.

How to read this page:
- Every claim cites a file and line, like `api/scripts/load_serving.ts:65`.
- "not verified" means the code in this repo does not show it, so I did not guess.
- "Automated" in this page means a person does not have to start it. By that meaning, nothing in this repo loads or refreshes data automatically (see section 3).
- CareBoard is a synthetic-data portfolio project. Only the Medicaid and Medicare spend tables come from public CMS data. Everything about patients, clinics, staff and policies is invented.

## 2. How to load more data

Today, from the `api` folder. Neon steps need `NEON_ADMIN_URL` and my explicit yes first (`CLAUDE.md`, "Ask before: touching Neon").

### Case A, a newer Medicare year

1. In `api/scripts/export_medicare.ts:10-11`, replace `SOURCE` with the new data.cms.gov file URL. The file must have the same columns: `Mftr_Name`, `Brnd_Name`, `Gnrc_Name`, `Tot_Spndng_YYYY`, `Tot_Clms_YYYY` (`:45-67`). Years are found from the column names (`:46-50`).
2. `npx tsx scripts/export_medicare.ts` (manual, needs internet). Read the printed class totals, the percent of Part D spend covered and the "left out on purpose" list (`:83-95`). These printouts are the only check. Nothing fails the run.
3. Commit the changed `data/medicare_part_d_annual.csv`.
4. `npx tsx scripts/load_serving.ts` for the local database; then, with my yes, `npx tsx scripts/load_serving.ts --neon` (`load_serving.ts:46-48`).

### Case B, a newer Medicaid quarter or year

1. In the diabetes-glp1-pipeline project, refresh its tables. The steps there: **not verified** from this repo.
2. Put the `SRC_*` settings in `api/.env` and run `npx tsx scripts/export_medicaid.ts`. Read the last four lines. `match: NO` means the grouped total differs from `analytics.diabetes_class_summary`. **The CSV is already written by then** (`export_medicaid.ts:35` writes, `:41` prints), so a mismatch does not stop anything.
3. Commit the CSV, then run `load_serving.ts` as in Case A step 4.

### What the load does

`load_serving.ts` does `TRUNCATE` and then `INSERT` for each table inside one transaction (`:51,65-66,72`). If anything fails, it rolls back and the old data stays (`:73-75`). It loads **all three** serving tables and reapplies `db/comments.sql` every time (`:52,70-71`).

## 3. Known gaps

Stated plainly:

1. **There is no Medicaid ingestion from CMS in this repo.** The Medicaid table arrives as a CSV exported from a different project's database. That hand-off is manual: someone runs `export_medicaid.ts` with `SRC_*` settings, commits the file, then runs the loader. What the other project does (download, cleaning, class assignment) cannot be seen from here.
2. **Medicare is fetched from CMS by a script in this repo, but not by a pipeline.** `export_medicare.ts` downloads one hard-coded file URL when someone runs it (`:10-11,40-41`). It keeps no copy of the raw file (it writes only the summed CSV, `:79-81`), records no file hash or download date, and has no check that the expected columns exist before it sums them.
3. **There is no scheduled refresh of any data.** The only scheduled workflows are `keepalive.yml` (every 10 minutes) and `digest.yml` (weekdays); I searched `.github/workflows` for `schedule`. Neon is updated only when I run a `--neon` command by hand.
4. **There are no freshness or row-count checks on load.** `load_serving.ts` prints the number of rows it loaded (`:67`) and nothing else: no expected minimum, no comparison with the previous load. `export_medicaid.ts` prints a total check but does not stop on a mismatch (see section 2, Case B). The database does have `app.data_inventory()` (row counts and latest period, `db/risk.sql:297-308`) and `app.data_checks()` (`db/risk.sql:310-366`), but these report after the fact, with fixed expectations (4 quarters, 5 years), and gate nothing. Where in the app they are shown: **not verified**.
5. **The Medicaid table is a manual CSV hand-off, and the CSV in git is the only copy this repo knows about.** CI and Neon get whatever was last committed. No table records when a serving table was loaded or from which file: there is no such table in `db/*.sql`, and the serving tables have no load-time column (`load_serving.ts:13-39`).
6. **The README and the CI script disagree.** `README.md:138` says its sequence is the same as the GitHub Action's, but `ci_setup.sh` does not run `ingest_policies.ts`, so the policy table is created but not filled in CI (`ci_setup.sh:9-19`). Whether any test fills it: **not verified**.
7. **Two statements in the repo are hedged, not verified:** the Medicare spend note says "as far as I know it is before manufacturer rebates" (`db/comments.sql:36`), and the Medicaid notes say small cells "may be hidden" (`db/comments.sql:7`).
8. **Re-seeding patients renumbers them** (section 0, `clinical.patients`).

## 4. What a pipeline step inside this repo would add

A short list, in the order I would build it. None of this exists today.

- **A raw schema.** Store each download as it came (for example `raw.cms_part_d_2024`), with the source URL, a file hash, the load time and the row count. This makes a load repeatable and lets a bad transform be rerun without downloading again.
- **A transform step.** A script or SQL that turns raw into the `serving` tables. Move the drug-class list into one table that both Medicaid and Medicare use, so the two lists cannot drift apart.
- **Quality checks that can stop the load.** Expected columns present; keys unique; row count within a range of the last load; no negative amounts; the grouped total matches the source total (today that last check only prints). Failures should leave the existing serving tables unchanged, which the transaction in `load_serving.ts` already does for database errors.
